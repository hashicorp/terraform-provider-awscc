# bigdiffer: generation & orchestration (Brick 6)

Working doc for the capstone brick — wiring the built pieces (discovery, change
detection, recipe derivation, gate, policy, block mutation) into one pipeline
that **generates the changed types for real and keeps the output**. May be
discarded once Brick 6 ships. Section refs point at `new-generation.md`.

## Thesis

The legacy flow regenerates all ~1580 types every run and gates in two
whole-corpus passes. bigdiffer instead generates **only New + Changed** (the
byte-compare already identifies them), **concurrently**, and keeps the emitted
`*_gen.go`. Validation is the front half of generation (§6): the same pass that
would "gate" now produces the code, so nothing is thrown away. `make build`
remains a final compile gate (a bonus, not the primary check).

## Investigation findings (the generator surface)

Grounded by reading the generators, not assumed:

- **Registration is self-contained.** Each generated file self-registers in its
  own `func init()` via `registry.AddResourceFactory` /
  `AddListResourceFactory` / data-source equivalents. There is **no central
  factory list** to keep in sync per type.
- **Three whole-corpus index files** — `internal/provider/resources.go`,
  `singular_data_sources.go`, `plural_data_sources.go` — carry (a) the
  `//go:generate` directive per artifact and (b) the **blank package imports**
  (`_ ".../internal/aws/<svc>"`) that cause the `init()`s to run. Generated by
  `schema/main.go` from the overlay. A New type in a *new* service package needs
  its import added here or its resource never registers; a New type in an
  existing package needs nothing. Re-emitting these three files wholesale from
  the overlay rows is cheap (no schema parsing) and is the safe approach.
- **Output layout:** `internal/aws/<svc>/<res>_<artifact>_gen.go` (+ `_test.go`),
  `-package <svc>`, cfschema read from `internal/service/cloudformation/schemas/`.
  `plan.go` already derives `<svc>`, `<res>`, and the file names; only the
  absolute roots need resolving (see config todo).
- **The engine to own** is small and clean:
  - `shared.GenerateTemplateData` — assembles `TemplateData` from a schema. Two
    CWD hazards to fix in our copy: the `last_resource.txt` debug write (drop it)
    and the CWD-relative `ParseServicesFile("../identity/names/services.hcl")`
    read (resolve an absolute path). It also calls `schemaIsDeRecursed` to set
    `codegen.Emitter.Deduplicate` (#3270) — our copy must preserve this. Takes a
    schema **file path** today; our copy takes the in-memory sanitized bytes the
    discovery sweep already holds (build the doc via
    `cfschema.NewResourceJsonSchemaDocument`, check `x-derecursed` on the bytes).
  - `common.Generator` — parses each template per-call (concurrency-safe) with a
    small funcMap (`Title`, `Split`), runs `go/format.Source`, writes the file.
    Copy as-is.
  - Six templates (`schema.tmpl` + `tests.tmpl` for resource / singular-DS /
    plural-DS), embedded today in each generator main. Copy and `//go:embed`.
  - `codegen.Emitter` has **no mutable package state** (verified) — safe to
    import and drive concurrently; no need to fork it.
  - The plural-DS generator does **not** go through schema emission; it builds
    its `TemplateData` from the CFN type name alone. Confirm its exact inputs
    when copying that path; it cannot fail the schema-emission gate by
    construction (§9).
- **A fourth aggregate:** `import_examples_gen.json`, regenerated from schemas by
  `import-examples/main.go`. Re-emit it after edits or it drifts.
- **`x-derecursed`** appears in **zero** cached schemas right now, so the dedup
  path is dormant — but preserve it; a `derecurse-schema.py` pre-pass can turn it
  on for a type at any time.

## Pipeline (the `-discover` path)

```
discover(ctx)                         # rows + sanitized bytes (have it)
  → detectChanges(disc, frozen, cache)  # new/changed/unchanged/frozen/missing
  → for each candidate (New|Changed), concurrently (errgroup):
        plan  = generationPlan(row)
        td    = ownedGenerateTemplateData(bytes, …)   # validate = front half
        emit  → temp dir: *_gen.go (+ _test.go), all artifacts
        gate  = success/typed-failure per artifact
        dec   = decide(class, gate, today)
        if not a freeze: stage {promote temp→real files, promote bytes→cache}
  → apply decisions to overlay (mutate existing / synthesize new blocks)
  → re-emit the 3 index files + import_examples_gen.json from the final overlay
  → re-sort overlay, write it
  → compile gate: go build ./internal/...  (failure feeds policy, re-runs)
  → report (per-candidate result + action)
```

Never-regress: emit to a temp dir and promote only on success; a broken Changed
type keeps its existing files + last-good cache and is frozen; a broken New type
is added suppressed and nothing is promoted for the failed artifact.

Incremental vs `-full`: default touches only New + Changed. `-full` regenerates
everything — required when the **templates or engine change**, since then even
byte-identical schemas produce different output. (A stored template/engine
version stamp could auto-detect this later.)

## Anticipated challenges (grounded)

1. **Index-file + `import_examples` regeneration.** The per-type files
   self-register, so the real aggregate work is re-emitting the three
   `internal/provider/*.go` index files and `import_examples_gen.json`. Cheap and
   deterministic from the overlay, but must run every time types are added or
   suppressed, or registration/imports go stale.
2. **Faithful `GenerateTemplateData` copy.** It assembles far more than the
   front-half emit (identifiers, timeouts, write-only paths, framework import
   flags, `IsGlobal`/`HasMutableIdentity` from `services.hcl`). The CWD fixes are
   trivial; the risk is silently dropping some behavior. **Mitigation: a parity
   test (below), built first.**
3. **`services.hcl` resolution.** Global-resource and mutable-identity flags come
   from it; a wrong path silently changes generated code. Resolve absolutely via
   config.
4. **Template ownership drift.** Once copied, our templates can diverge from the
   legacy ones during the transition. The parity test guards this until the
   legacy generators are deleted.
5. **Dedup / `x-derecursed`.** Dormant now, but our copy must set
   `Emitter.Deduplicate` exactly as legacy does, or de-recursed schemas would
   regress silently.
6. **Concurrency proof, not assumption.** The engine looks clean; prove it —
   `-race` on concurrent generation of many types **plus** the parity
   byte-compare. (We already learned to verify rather than assume.)
7. **Compile-gate scope.** `go build ./internal/...` is the safe net (covers the
   index/import files); affected-packages-only is faster but risks missing
   registration breakage.
8. **Determinism.** Generated output must be byte-stable run-to-run (map
   iteration order, sorting) for clean diffs and a meaningful parity test.

## The correctness guarantee: a parity test

Generate a representative sample through bigdiffer's owned in-process path and
through the legacy generator, and byte-compare. Identical output proves the
copy/concurrency introduced no drift from the trusted generators. This is the
single most valuable thing to build early; every other challenge is de-risked by
it.

## Configuration todo (evaluation)

An **external config file** is low value here: awscc is static, and the overlay's
`defaults` block already centralizes the schema-related settings
(`schema_cache_directory`, `terraform_type_name_prefix`) plus `meta_schema`. A
second file would compete with `defaults` for little gain.

An **in-code `config` struct** is worth doing, for exactly the
documentation / clarity / lever-centralization reasons: today paths and tunables
are scattered across flag defaults and package constants (`discoverRegion`,
`discoverConcurrency`, cache/overlay/checkout paths, `dateLayout`), and Brick 6
adds more (output root `internal/aws`, the three index-file paths,
`import_examples` path, `services.hcl` path, meta-schema path, generation
concurrency, temp dir, full vs incremental). Gathering these into one struct
derived once from the overlay `defaults` + flags + sensible constants — and
threaded explicitly through the pipeline — centralizes the levers, documents them
in one place, and improves testability (inject paths instead of the brittle
CWD-relative assumptions we already had to work around in `gate_test.go`).

**Recommendation:** add a `config` struct as the first orchestration step (single
source of truth for paths, region, concurrency, prefix, mode); resolve all
relative-to-overlay paths to absolute there. Defer/decline an external config
file unless a concrete need arises.
