# Held artifacts: gating the unchanged corpus (`codegen_error` / `toolchain_error`)

> **Transient design doc.** This is the working design for the `held` feature
> while it is being implemented. When it lands, the durable parts fold into
> `bigdiffer-design.md` (§6 "The gates" and §7's policy table) and this file is
> deleted. It exists so the gap, the failure modes, their nuance, and the
> required behavior are stated cleanly in one place before code is written.

## 1. The gap

Both of bigdiffer's gates — generation and compile (`bigdiffer-design.md` §6) —
run only on **New** and **Changed** types. A type whose live CloudFormation
schema is byte-identical to the cached copy is classified `statusUnchanged`
(`change.go`) and skipped entirely. That is exactly right for *schema* drift:
if nothing about the input changed, there is nothing to regenerate.

But it means a change to the **generation machinery itself** — a template, the
`codegen/` package, the naming logic, or the Go toolchain and its dependencies
— is never exercised against the ~1580 types whose schema did not move this
week. Their committed `*_gen.go` output silently ages: it was produced by an
older engine and is never re-derived unless that specific type's schema happens
to change.

Today the only thing that would catch such a regression is
`TestFullCorpusParity`, and only for as long as its byte-for-byte comparison
against the legacy generators exists — and that comparison is itself slated for
removal once the legacy engine is deleted (`bigdiffer-design.md` §10). Once it
is gone, a machinery regression on an unchanged-schema type goes undetected
until something downstream breaks. **Silent staleness is the gap.**

The core requirement that follows: when an engine change breaks generation for
some types, a bigdiffer run must be **loud about it**. A codegen change that
quietly degrades output for a few types, noticed by no one, is the specific
failure this feature exists to prevent.

## 2. The fix, in one line

Run **every** type through generate-then-compile every `-update`, not just
New/Changed. The gates already exist, are deterministic, and are fast (the
full-corpus offline regeneration is on the order of tens of seconds; the
compile gate is a few seconds). A schema-unchanged type that now fails a gate
is a machinery regression *by construction* — nothing about the type changed,
so the tool is the only variable.

## 3. Failure modes

A schema-unchanged failure is **not** automatically a codegen defect. bigdiffer
already holds both the freshly regenerated bytes (in memory, before promotion)
and the committed file (on disk), so a cheap byte-comparison — no second
compile — separates two distinct causes:

| Mode | Regenerated bytes vs. committed | Diagnosis |
|------|--------------------------------|-----------|
| `codegen_error` | **differ**, and the new output is what fails | This run's codegen produced something different from what is shipping, and the different output broke. The committed file — unchanged, still in production — is known-good. |
| `toolchain_error` | **identical**, and that same file now fails | Codegen produced the exact bytes it always has; the environment around them (Go version, a dependency bump, a shared runtime package) changed. The committed file is not "known-good" in the same sense — it was good under the *previous* environment. |

Both share one symptom ("schema unchanged, gate fails") and one immediate
response — **the committed file is not replaced** — so they are one mechanism
for detection and diagnosis, with two reason categories rather than two
different mechanisms. They diverge on what the run does next (§5).

## 4. The nuance: cause is not disposition

The byte-diff labels the **cause**. It is the wrong thing to decide the
**release disposition** on. The invariant that actually must hold is *"the
committed tree builds,"* and §6's compile-gate fixpoint already computes
exactly that: on failure it reverts the offending artifact to its committed
file and rebuilds.

- **`codegen_error` → revert goes green.** The committed file is genuinely
  good; discarding the bad new bytes yields a building tree. Safe to hold and
  ship.
- **`toolchain_error` → revert stays red.** The committed file *is* the file
  that just failed (the regenerated bytes were byte-identical to it), so
  reverting changes nothing — the tree this run would commit does not build
  under the current environment.

So the hold-vs-block decision keys on the **post-revert build result**, not on
the byte-diff. This also correctly handles the case the byte-diff alone would
mislabel: regenerated bytes differ (looks like `codegen_error`), yet the
committed file *also* fails under a bumped toolchain — post-revert red, so it
must block, not ship.

Two more points of nuance:

- **Attribution reuses the existing blame-mapping.** A build failure is
  attributable when `go build`'s `file:line:col` maps cleanly to a staged
  artifact/package — the same mapping the §6 fixpoint already does. That covers
  a dependency bump breaking *some* resources and not others: each affected
  artifact is identified individually. A blamed file mapping to nothing staged
  (a pre-existing base-tree break, or a bug in bigdiffer's own emitted
  registration file) is unattributable exactly as §6 already defines it and
  hard-errors the run — that case is not `held`.
- **Per-artifact, matching `suppress_*`.** The trio — resource, singular data
  source, plural data source — each holds independently. A list resource is not
  a fourth bucket: it is an attribute of the resource artifact (gated by whether
  the plural data source is present — §6's list-resource coupling guard), so a
  list-resource-specific failure is the *resource's* hold, with the reason text
  naming the list resource specifically.

## 5. How bigdiffer should behave

### 5.1 `codegen_error`: hold, mark, ship — loudly

- Keep the committed file (never regress).
- Record a per-artifact marker in the overlay (§6 shape below) with the
  `codegen_error` category and a detail string.
- Let the release proceed — the committed tree builds — **but** surface the
  hold prominently (§5.4). The provider ships last-good output for that type;
  a human must still fix the engine.

### 5.2 `toolchain_error`: block the run

- The committed tree will not build under the current environment, so the run
  **cannot** produce a shippable result. Hard-error, with a per-artifact report
  of every `toolchain_error` and its blame. Nothing is promoted; nothing is
  persisted (a `toolchain_error` never becomes a committed overlay marker — it
  is a run-blocking condition, not a durable state).
- Resolution is a code fix (or reverting the environment change), then re-run.

### 5.3 Volume threshold (a `codegen_error` safety valve)

`toolchain_error` already blocks regardless of count, so this is only about a
large `codegen_error` batch: each is individually holdable and shippable, but a
run that holds *hundreds* of them is a systemic codegen regression, and
completing "successfully" while silently skipping a large fraction of the
corpus would bury the signal. If the held count crosses a threshold
(illustrative, not committed: ~10–20% of attempted types, or a held count in
the low hundreds), hard-error instead of completing — the same "abort on
aggregate" instinct, triggered by volume rather than by unmappable blame.

### 5.4 Noisy reporting (the point of the feature)

An engine regression must be **impossible to miss**. Three layers, so it is
caught no matter which path introduced it:

1. **End-of-`-update` summary.** After the run, print a distinct, prominent
   section (not interleaved with per-type progress) that states plainly: *N
   artifacts were held this cycle and NOT updated*, grouped by reason category,
   each with its type, artifact, and blame. A `toolchain_error` spike after a
   dependency bump must read as one event, not scatter among unrelated
   `codegen_error` rows. If the run blocked (§5.2) or tripped the threshold
   (§5.3), that headline comes first. This is a first-class part of the change
   report a human reviews before commit — held rows get their own section,
   separate from the frozen/suppressed section, because a held row is neither
   backlog nor something a human approves: it is bigdiffer telling its own
   maintainers "the last engine change broke this; it needs a code fix, not an
   overlay edit."
2. **The committed diff.** `codegen_error` markers land in `all_schemas.hcl`,
   so they appear in the `-update` PR diff — a reviewer sees exactly which types
   were held.
3. **`-check` fails on them.** `-check` (offline, runs on every PR) flags any
   `held` marker as an anomaly (parallel to today's `anomalyProblems()`), so a
   held marker that survives past the PR that should have fixed it fails CI. A
   held marker is never a silently-acceptable steady state.

### 5.5 Catching engine changes at PR time

`-update` runs weekly and needs AWS, so on its own it catches an engine
regression only at the next weekly cycle. To close the window between an
engine-touching PR (templates, `codegen/`, naming, `go.mod`) and that cycle,
the same full-corpus generate-then-compile can run **offline** — `-generate`
already regenerates the whole corpus from the committed overlay and cache with
no AWS. A CI gate that runs `-generate` and then `go build ./...` (and asserts
no unexpected drift) catches `codegen_error` immediately, on the PR that
introduces it. This is the natural replacement for `TestFullCorpusParity`'s
role once the legacy comparison is gone — self-referential (current engine vs.
committed output) rather than legacy-referential. *(Detail to be worked out in
implementation — noted here so the reporting story is complete.)*

### 5.6 Self-clearing

Because the full corpus is re-attempted every `-update`, a held artifact is
re-evaluated every run. The run after the regression is fixed — in codegen, or
by the environment moving again — that artifact regenerates and compiles
cleanly, is promoted, and its marker is cleared automatically. No `-heal` step
is needed for this category, unlike `unknown`/`manual` rows.

## 6. Overlay markers (near-term shape)

For this implementation, `held` follows the existing two-attribute-per-fact
convention, matching `suppress_*_generation`/`suppression_reason_*` and
`frozen_since`/`frozen_reason` so it ships consistent with the levers already in
the overlay:

- `held_resource` / `held_singular_data_source` / `held_plural_data_source`
  (bool).
- `held_reason_resource` / `_singular_data_source` / `_plural_data_source`
  (string, `category: detail` shape; category is `codegen_error` — a
  `toolchain_error` blocks and is never persisted, §5.2).

`held` is **orthogonal** to both existing levers and must not be conflated with
either:

- **Not `frozen_since`.** Freezing pins the *schema* (and stops future refresh).
  A held type's schema is fine and must keep refreshing the moment it actually
  changes; only the machinery is at fault. A held artifact never sets
  `frozen_since`.
- **Not `suppress_*`.** Suppression is a standing, human-owned decision to *not
  generate* an artifact. `held` is the tool temporarily unable to keep a promise
  it already kept last week; the intent is still "generate this."

> The longer-term question of collapsing `suppress`/`held`/`frozen` into one
> self-describing attribute per fact (and the per-artifact-vs-per-type
> granularity split that entails) is **out of scope here** — see
> `bigdiffer-design.md` "Deferred and future work". `held`'s shape is chosen to
> be additive toward that direction, not to prejudge it.

## 7. Implementation sketch (to expand)

Rough touchpoints, to be filled in as the design is refined into code:

- `change.go` — the full-corpus sweep: process `statusUnchanged` types through
  generate-then-compile instead of short-circuiting.
- byte-comparison of regenerated vs. committed bytes to tag the cause.
- `compile.go` — reuse the fixpoint's blame-mapping and post-revert build result
  as the hold-vs-block discriminator.
- `policy.go` — the `held` overlay action and the `codegen_error` /
  `toolchain_error` categories.
- `main.go` — the end-of-run held report section and the `-check` `held`
  anomaly.
- run-level: the volume threshold and the `toolchain_error` block.
- `suppressed-and-frozen.md` — document the new categories.

## 8. Open questions

- Exit code of `-update` when it completes with `codegen_error` holds: exit 0
  with the loud banner (the tree is shippable, and `-check` is the hard gate),
  or non-zero to force attention? Leaning exit 0 + banner + `-check`.
- Exact threshold value and whether it is a fraction, an absolute count, or both.
- Whether the PR-time offline guard (§5.5) is a Go test, a `make` target, or a
  CI step — and how it distinguishes expected drift (a legitimate engine change
  that should be regenerated and committed) from a regression.
